# wallis v2

This document defines v2: a full rewrite of the authoring and calling
surface. The rewrite reuses the parts of v1 that real use validated: the
journal, sessions, workspace layers, content-addressed caching and the pi
executor. It drops the machinery that grew around interaction and around
defending against attackers who are not in the threat model.

Status: **design, for review.** Nothing in `v2/` exists yet. v1 stays in
place and keeps working until v2 passes the acceptance below.

## 1. Purpose and threat model

wallis runs agent workflows that are cached, reproducible and safe to leave
unattended. A workflow is ordinary TypeScript code calling typed nodes:

- **commands:** sandboxed programs;
- **agents:** pi agent loops;
- **tool sources:** custom tool modules or MCP servers;
- **nested workflows.**

**Threat model.** wallis is the interpreter of its author's own code, and its
permissions are a subset of the agent that calls it, usually Claude Code. It
does **not** defend against a malicious workflow author or a malicious
sub-agent. Its sandbox has exactly two jobs:

1. **Prevent accidents.** A sub-agent or a command can't damage host files by
   mistake (a wrong `rm`, a wrong path, an overwrite).
2. **Make dependencies explicit.** Every file a call reads is declared, so
   cache keys are sound and results reproduce (hermetic, as in Bazel or
   Nix).

A determined bypass is acceptable. Reviews and tests use this model, and
nothing else.

When a sub-agent reaches outside its view, that is a workflow design error,
not a security event. It gets a clear, actionable error ("`/x` is not in your
workspace; this workflow did not provide it"), plus a diagnostic that tells
the author which volume or input is missing.

## 2. Shape

- An npm package, `wallis`, plus a skill that teaches agents to use it.
- **No CLI, no MCP server, no daemon.** Callers use the JS API from a script
  or from `node --input-type=module -e '…'`. Node 26 strips TypeScript types
  natively.
- Long runs detach as an ordinary detached Node process. The run directory is
  the single source of truth, so anyone can read it.
- Platform: Linux, because the sandbox uses bwrap. systemd is not required.
- The MCP **client** stays: workflows can use existing MCP servers as tools.

## 3. Naming

Three kinds of names, each with one style:

| Kind | Style | Names |
|---|---|---|
| Nodes and resources | lowercase noun | `workflow`, `command`, `agent`, `sandbox`, `toolset`, `mcp`, `channel` |
| Schema builders | Capitalized (like TypeBox `Type.Object`) | `Artifact`, `Tree`, `Recv`, `Send` |
| Operations | verb | `run`, `attach`, `resume`, `fork`, `stop`, `send`, `next`, `exportOutput`, `list`; `ctx.call`, `ctx.spawn`, `ctx.loop` |

## 4. Authoring API

One file, `workflow.ts`, holds everything a workflow declares. Custom tool
modules are the only separate files, because they run in their own process.
Split a workflow into more modules only when it grows or is shared; that is
a convention, not a rule.

```ts
import { workflow, command, agent, sandbox, toolset, Artifact, Recv, Send, Type } from "wallis";

const dt = sandbox({
  requires: ["darktable-cli", "nona", "python3"],
  volumes: ["./scripts:/scripts:ro", "dt-cache:/root/.cache/darktable"],
  environment: { OMP_NUM_THREADS: "4" },
});

export const stitch = command({
  sandbox: dt,
  input:  Type.Object({ frame: Frame }),
  output: Type.Object({ neg: Artifact("image/tiff") }),
  run:    ({ frame }) => ["python3", "/scripts/stitch.py", frame.pto.path, frame.halves[0].path, frame.halves[1].path],
  parse:  (r) => ({ neg: r.file("neg.tif") }),
});

const ente = toolset<typeof import("./tools/ente.ts")>("./tools/ente.ts", { network: "host", secrets: ["ENTE_TOKEN"] });

export const uploader = agent({
  model: "default",
  prompt: "Upload every file to the album; handle errors yourself; confirm with list.",
  input:  Type.Object({ album: Type.String(), files: Type.Array(Artifact("image/jpeg")), guidance: Recv(Type.String()) }),
  output: Type.Object({ uploaded: Type.Integer(), notes: Type.String() }),
  tools:  [ente.upload, ente.list],
});

export const develop = workflow({
  input:  Type.Object({ frames: Type.Array(Frame), look: Look, only: Type.Optional(Type.Array(Type.String())), size: Size }),
  output: Type.Object({ images: Type.Record(Type.String(), Artifact("image/jpeg")) }),
  run: async (ctx, { frames, look, only, size }) => {
    const picked = only ? frames.filter((f) => only.includes(f.id)) : frames;
    const out: Record<string, ArtifactRef> = {};
    for (const f of picked) {                                   // sequential: plain code controls concurrency
      const { neg } = await ctx.call(stitch, { frame: f });
      out[f.id] = (await ctx.call(render, { neg, look, size })).jpg;
    }
    return { images: out };
  },
});

export default workflow({
  input:  Type.Object({ roll: develop.input, album: Type.String() }),
  output: Type.Object({ images: develop.output.properties.images, report: uploader.output }),
  run: async (ctx, { roll, album }) => {
    const { images } = await ctx.call(develop, { ...roll, size: "full" });   // nested workflow
    const guidance = ctx.inbox("guidance", Type.String());                    // steerable from outside
    const [report] = await ctx.call(ctx.session(uploader), { album, files: Object.values(images), guidance });
    return { images, report };
  },
});
```

### 4.1 Nodes

| Node | Definition | Called by | Cached |
|---|---|---|---|
| `command` | sandbox, `run(input) → argv`, `parse(result, input) → output` | `ctx.call` | globally, by content (§5.3) |
| `agent` | model alias, prompt, input, output, tools, optional `workspace` | through a session: `ctx.call(session, input)` → `[output, nextSession]` | per run and its forks |
| `workflow` | input, output, `run(ctx, input)` | `ctx.call`, or a caller's `run()` | its calls are cached |
| custom tool | a module exporting pi `AgentTool`s plus `annotations` and `replay` | an agent's `tools`, or `ctx.call(lib.tool, input)` | per run, with write epochs (§5.6) |
| MCP tool | `mcp(json, overlay)`, then `server` or `server.tool` | same as a custom tool | same as a custom tool |

- **Nodes are plain values.** Import them and call them; a workflow does not
  list the nodes it uses.
- **Model aliases** come from project configuration, so there is no `env`
  argument.

### 4.2 Agents

- **Sessions.** `ctx.session(agent, { from?: Tree })` creates an immutable
  session value. Calling it returns `[output, next]`. Calling the same value
  twice is a branch.
- **Workspace.** `workspace: { access: "read" | "write" | "exec", sandbox? }`.
  - Without the field, access is inferred from the signature: Artifact
    inputs give `read`, Artifact outputs give `write`. `exec` is never
    inferred.
  - The file tools (pi-compatible `read`, `write`, `edit`, `ls`, `bash`) come
    from the access level, never from `tools`.
  - `ctx.files(s)` returns the session's `/w` as a Tree.
- **Tools.** `tools` holds custom tools and MCP tools only. Tools annotated as
  writing outside produce a warning in `describe()`, nothing more.
- **Channels.** Agents have no channels unless their signature declares
  `Recv` or `Send` (§6).
- **Missing information.** An agent that lacks information either asks
  through a declared `Send` channel, or ends its call with an output such as
  `{ type: "need_info", question }`, which the workflow returns to its caller.

### 4.3 The body

`ctx.call`, `ctx.session`, `ctx.files`, `ctx.spawn`, `ctx.loop`, `channel`,
`ctx.inbox`, `ctx.outbox`. That is all.

- **`ctx.spawn(async (ctx) => …)`** is the only concurrency primitive. It
  gives the task its own deterministic branch at spawn time. `ctx.map(items,
  f)` is sugar for one spawn per item. To limit concurrency, use plain code:
  a loop, or batches.
- **`ctx.loop(init, (ctx, state) => next(s) | done(o))`** is a typed fold.
  State and output types are separate, and each iteration is a branch.
- **Errors.** A failed call throws one `NodeFailed` whose `reason` is a typed
  union.

### 4.4 Sandboxes

`sandbox({...})` is a subset of a compose service:

- **`requires`:** programs that must exist. Each is called by its real path,
  with its `argv[0]` name kept. Only the program and its prefix's `lib`,
  `lib64`, `libexec` and `share` become visible.
- **`volumes`:**
  - `"<host>:<target>:ro"` is a read-only bind. The mode is required, and
    there is no `rw`. Host paths are relative or start with `~/`.
  - `"<name>:<target>"` is a named volume: a wallis-managed cache, writable
    by commands and tool sources, read-only for agents, and left out of
    cache keys.
- **`environment`**, **`devices`**, **`network: "none" | "host"`** (default
  `"none"`), and **`image`** (reserved for a future Docker backend).

## 5. Semantics

### 5.1 Runs

A run evaluates one workflow on one input.

- **Pure runs.** A run that declares no inbox and no outbox is a pure
  function: it finishes or fails.
- **Interacting runs.** A run that declares them interacts only through those
  typed channels (§6).
- **Interruption.** A run can be stopped at any time and resumed. Completed
  calls are reused; only calls that were in flight run again.

### 5.2 The journal

- **One commit point.** The run log is append-only and is the single commit
  point. Every side file is either a content-addressed blob that an event
  names, written before that event, or a cache derivable from the log.
- **Attempts.** Restarts and forgets append attempts; nothing is deleted.

### 5.3 Caching

- **Commands** are cached **globally** under `~/.cache/wallis/`. The key is
  the computed argv, the environment, the sandbox digest, the content digests
  of the bound volumes, and the input artifacts.
  - A new run therefore reuses expensive deterministic work without forking.
  - The stored result is the raw process result. The current `parse` is
    re-applied on every hit, so changing `parse` never needs a rerun.
  - `cache: false` on a command opts out, for nondeterministic or networked
    commands.
- **Agent calls and tool calls** are cached per run and its forks, because
  they are not deterministic.
- **Fork.** `fork(run, { input?, forget? })` copies a run's journal and
  re-executes. It is how agent dialogues are reused under a changed input,
  and how a chosen call is redone.

### 5.4 Determinism

- **QuickJS.** The body runs in QuickJS: no I/O, a seeded `Math.random` and a
  virtual clock. This is the one place where reproducibility is enforced by
  structure, not by convention.
- **Call ids** come from the branch position and the program order within the
  branch, assigned synchronously.
- **Channels** have a single sender and no `select`.

### 5.5 Identity

Identity is a digest or a structural position, never a name. Names are
labels:

- a tool is (bundle digest, export key), or (MCP server, tool);
- a node is its definition digest;
- a workflow is its bundle digest.

### 5.6 Tool sources

- **Write epochs.** Each tool source has a write epoch: a hash chain over the
  write-capable calls made to it, in program order per branch. Every call to
  that source includes the epoch in its key, so a read after a changed write
  misses.
- **Nondeterministic output.** When a call re-executes under the same key and
  its output digest differs, wallis notes a `nondeterministic_output`
  warning.

## 6. Channels and interaction

Channels follow Go's model.

- **Creating.** `channel<T>(buffer?)` creates one in the body. A full channel
  narrows to `Recv<T>` or `Send<T>`.
- **Closing.** `close()` is done by the sender. A receiver drains the
  remaining messages and then sees the end, or iterates with `for await`.
- **No `select`.** A channel has one sender; a second sender is a typed
  refusal.
- **Journaling.** Channel operations between body tasks are not journaled;
  they are deterministic on replay.

**In an agent's signature:**

- **`Recv(T)`:** messages enter the agent's **next turn** automatically.
  - Several messages that arrived during one turn are delivered together.
  - `{ interrupt: true }` aborts the current turn.
  - An agent with an open `Recv` and nothing to do waits. Once the channel is
    closed and the agent stops, it must submit.
  - Each message is journaled with the turn it was delivered after.
- **`Send(T)`:** a `send` tool that never blocks the agent. The agent may
  send a question and keep working.

**Across the run boundary:**

- **`ctx.inbox(name, T)`** returns a `Recv` fed from outside with
  `attach(id).send(name, value, { replyTo? })`. Messages sent while the run is
  stopped persist and are delivered on resume.
- **`ctx.outbox(name, T)`** returns a `Send` whose messages persist in the run
  directory and never block. The caller reads them with
  `attach(id).next({ timeout })`, which returns `message | finished | timeout`.
- **Message ids** are deterministic: `<channel>/<seq>`, prefixed with the run
  id when they must be globally unique. External messages are numbered on
  arrival and journaled. Replies name the message they answer with
  `replyTo`.

This one mechanism replaces v1's `ask`, steer, orchestrator nodes,
approvals, pending items and `submit`:

- **Asking:** a `Send` for questions plus a `Recv` for answers.
- **Steering:** a `Recv` inbox.
- **Approval:** body code writes a request to an outbox and waits on an
  inbox.

## 7. Caller API

```ts
import { run, attach, list } from "wallis";

const r = await run(workflow, input, { detach?: true, onExit?: "<shell command>" });
r.id;                                   // run id: <workflow>-<time>-<rand>
await r.status();                       // done, running and hit counts, elapsed time
await r.tree();                         // call tree, intermediate outputs, loop iterations
await r.transcript("uploader");         // an agent call's dialogue
await r.next({ timeout: "110m" });      // message | finished | timeout
await r.send("guidance", "rename the album", { interrupt: true });
await r.stop();  await r.resume({ detach: true });
const f = await r.fork({ input: { ...r.input, look: L2 }, forget: [] });
await r.exportOutput("~/Pictures/150ND610-work/final-v2");
attach(id);  await list("./negative/workflow.ts");
```

- **Detaching.** `detach` starts the run as a detached Node process and
  returns at once. `onExit` runs when the run process exits normally.
- **Long waits.** Harnesses limit background commands (Claude Code: 2 hours),
  so `next({ timeout })` returns `timeout` with progress, and the caller
  waits again.
- **Where runs live.** A run belongs to the project of its workflow file (the
  nearest ancestor with `.wallis/` or `package.json`), not to the cwd.
- **Locking.** A run directory has a lock file, so two processes never write
  the same run.

## 8. Removed in v2

| Removed | Why |
|---|---|
| Orchestrator nodes, the agent `ask` tool, `submit`, pending items, approvals | replaced by channels (§6) |
| `send`/`interrupt`/`steer` as special verbs, `steerable`, node lookup by name | a `Recv` inbox |
| Ownership, `claim`, owner detection | runs are local files; a lock file is enough |
| The CLI (22 subcommands) and the MCP server | the JS API |
| Adversarial hardening: the TOCTOU openat walk, host re-parsing of declarations, device and environment guards, prototype-pollution checks, the escape-suite gate | outside the threat model (§1) |
| Resource limits and the systemd dependency | plain code controls concurrency; the OS OOM handler catches runaways |
| Foldable, `ctx.parallel`, `observe`, budgets, seven error classes, bind snapshots | unused, replaced by `spawn` and `map`, or simplified (§4.3, §5.3) |
| The `env` argument and declared node lists | nodes are plain values |
| Storing command scratch dirs beside their artifacts (2x storage) | artifacts only |

## 9. Carried over from v1

These modules are ported and adapted, not rewritten:

- the pi executor (`pi.ts`): retries, per-turn checkpoints, compaction,
  image token estimates (`images.ts`);
- the artifact store and Trees (`artifacts.ts`), and workspace layers
  (`layers.ts`, minus the userland overlay emulation);
- the toolset bundler and runner (`toolsets.ts`, `toolset-runner.ts`), and
  the MCP client (part of `tools.ts`);
- volume parsing (`volumes.ts`, `sdk/volumes.ts`) and the `requires`
  resolution (`hostbin.ts`, part of `confine.ts`);
- the log, the store and dialogues (`log.ts`, `store.ts`, `dialogues.ts`),
  including the atomic meta writes and the repair of a truncated last line;
- in the core: `ids`, `digest` and `value`, plus the journal, attempts,
  session hashing and write-epoch logic from `run.gleam`.

These tests are ported wherever their semantics survive:

- `cache`, `command-cache`, `sessions`, `workspace`, `epochs`, `fork-input`,
  `loop`, `recovery`, `resume`, `artifacts`, `images`, `toolsets`, `volumes`,
  `identity`, `pi`, `siderius`;
- `run_test.gleam`;
- the escape-suite cases that test correctness and hermeticity rather than
  attacks (static symlinks resolved in the sandbox view, `requires` exposure,
  no network for agents).

The differential check (state rebuilt from the log equals the live state)
stays on for every test.

## 11. Open questions

1. **Keep QuickJS for the body?** Proposed: yes (§5.4). The alternative is
   plain Node: less code and direct npm use, but determinism by convention
   only.
2. **Global cache size.** Proposed: least-recently-used eviction with a
   default cap of 50 GB, configurable.
3. **Budgets.** Proposed: none in v2. The caller watches cost; agent turn
   limits stay.
4. **Commands with network.** Proposed: allowed when declared
   (`network: "host"`), shown in `describe()`, with `cache: false` the
   default for such commands.
